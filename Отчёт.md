# Отчёт по приложению WorkoutTracker

## Доменная область приложения

WorkoutTracker — это приложение для учёта силовых тренировок. Пользователь может зарегистрироваться, войти в аккаунт, создавать тренировки на выбранную дату, добавлять в тренировку упражнения и фиксировать подходы: номер подхода, количество повторений и вес.

Приложение решает задачу персонального тренировочного дневника: хранит историю тренировок, позволяет просматривать отдельную тренировку, добавлять новые упражнения и считать базовую статистику по тренировочным данным.

## Стек реализации

### Backend

- ASP.NET Core Minimal API на .NET 10.
- Entity Framework Core для работы с базой данных.
- PostgreSQL как основная база данных.
- ASP.NET Core Identity для регистрации, входа и хранения пользователей.
- Cookie authentication для авторизации пользователя.
- Npgsql.EntityFrameworkCore.PostgreSQL как провайдер PostgreSQL.
- Scalar/OpenAPI для просмотра API в development-окружении.

### Frontend

- Blazor WebAssembly на .NET 10.
- Razor-компоненты и CSS isolation.
- HttpClient для запросов к API.
- Cookie-based auth state provider для проверки текущего пользователя.
- MudBlazor подключён как UI-библиотека.

### Deployment

- Dockerfile для API.
- Dockerfile для Blazor Client.
- nginx для раздачи Blazor WebAssembly и reverse proxy к API.
- docker compose для запуска `postgres`, `api` и `client`.
- HTTPS на уровне nginx через сертификаты, примонтированные в контейнер.

## Основные сущности доменной области

### ApplicationUser

Пользователь приложения. Расширяет стандартного пользователя ASP.NET Identity и добавляет поле `Name`.

Основные поля:

- `Id`
- `Email`
- `UserName`
- `Name`

Пользователь является владельцем своих тренировок и упражнений.

### Workout

Тренировка пользователя.

Основные поля:

- `Id`
- `Date`
- `Note`
- `UserId`
- `WorkoutExercises`

Тренировка принадлежит конкретному пользователю и содержит список упражнений через сущность `WorkoutExercise`.

### Exercise

Упражнение пользователя.

Основные поля:

- `Id`
- `Name`
- `UserId`
- `WorkoutExercises`

Упражнения хранятся отдельно от тренировок, чтобы пользователь мог выбирать уже созданное упражнение повторно.

### WorkoutExercise

Связь между тренировкой и упражнением.

Основные поля:

- `Id`
- `WorkoutId`
- `ExerciseId`
- `Sets`

Эта сущность показывает, какое упражнение было выполнено в конкретной тренировке.

### Set

Подход в упражнении.

Основные поля:

- `Id`
- `WorkoutExerciseId`
- `SetNumber`
- `Reps`
- `Weight`

Подход хранит конкретные тренировочные значения: количество повторений и вес.

## Соответствие методологии 12 факторов

### 1. Codebase

Приложение хранится в одном репозитории `WorkoutTracker`. Внутри репозитория несколько проектов:

- `WorkoutTracker.Api`
- `WorkoutTracker.Client`
- `WorkoutTracker.Core`

Это соответствует фактору: один codebase используется для разработки и развёртывания приложения. Разделение на проекты не нарушает принцип, так как они являются частями одного приложения.

### 2. Dependencies

Зависимости backend и frontend объявлены явно в `.csproj` файлах.

Примеры зависимостей API:

- `Microsoft.EntityFrameworkCore`
- `Microsoft.AspNetCore.Identity.EntityFrameworkCore`
- `Npgsql.EntityFrameworkCore.PostgreSQL`
- `DotNetEnv`
- `Scalar.AspNetCore`

Примеры зависимостей клиента:

- `Microsoft.AspNetCore.Components.WebAssembly`
- `Microsoft.AspNetCore.Components.Authorization`
- `Microsoft.Extensions.Http`
- `MudBlazor`

Также Dockerfile выполняет `dotnet restore`, поэтому зависимости восстанавливаются при сборке образов. Фактор в целом соблюдён.

### 3. Config

Окружение-зависимые настройки вынесены из кода.

Для API используются переменные окружения:

- `ASPNETCORE_ENVIRONMENT`
- `DB_HOST`
- `DB_PORT`
- `DB_NAME`
- `DB_USER`
- `DB_PASSWORD`
- `CLIENT_URL`
- `CLIENT_HTTPS_URL`

Файл `.env` не должен коммититься в репозиторий. Для примера используется `.env.example`.

Подключение к базе данных собирается из переменных окружения в `AddProjectDatabase`. CORS также настраивается через переменные окружения.

Частичное ограничение: клиентский Blazor WebAssembly не может безопасно читать приватные переменные окружения, потому что выполняется в браузере. Поэтому публичный адрес API хранится в `wwwroot/appsettings.json` и `wwwroot/appsettings.Production.json`. Это допустимо, так как URL API не является секретом.

### 4. Backing Services

PostgreSQL рассматривается как внешний backing service. Приложение не привязано к конкретной локальной базе: параметры подключения передаются через переменные окружения.

В Docker Compose база запускается отдельным сервисом `postgres`, а API подключается к ней по имени сервиса `postgres` внутри Docker-сети.

Фактор соблюдён.

### 5. Build, Release, Run

В проекте разделены этапы:

- build: сборка приложения в Dockerfile через `dotnet restore` и `dotnet publish`;
- release: образ запускается с конкретными переменными окружения из `.env`;
- run: контейнеры запускаются через `docker compose up`.

Миграции базы данных выполняются отдельной командой `dotnet ef database update`, а не смешиваются с кодом обработки HTTP-запросов.

Фактор соблюдён частично: полноценный release pipeline пока не автоматизирован, но структура приложения уже позволяет разделять сборку, конфигурацию и запуск.

### 6. Processes

API работает как stateless process: состояние пользователя, тренировки, упражнения и подходы хранятся в PostgreSQL, а не в памяти процесса.

Blazor Client является статическим frontend-приложением, которое раздаётся nginx.

Авторизация использует cookies. Это допустимо, так как состояние сессии хранится на стороне клиента в cookie, а пользовательские данные остаются в базе.

Фактор в целом соблюдён.

### 7. Port Binding

API самостоятельно поднимает HTTP-сервер через Kestrel и слушает порт `8080` внутри контейнера:

```dockerfile
ENV ASPNETCORE_URLS=http://+:8080
EXPOSE 8080
```

Frontend отдаётся nginx на портах `80` и `443`. nginx также проксирует API-запросы внутрь Docker-сети на `api:8080`.

Для внешнего пользователя открыты только `80` и `443`, API и PostgreSQL не публикуются наружу.

Фактор соблюдён.

### 8. Concurrency

Приложение разделено на несколько процессов:

- `client` — nginx со статическим frontend и reverse proxy;
- `api` — ASP.NET Core API;
- `postgres` — база данных.

Теоретически API можно масштабировать горизонтально, подняв несколько экземпляров за reverse proxy. Текущее compose-окружение запускает один экземпляр API, потому что для учебного проекта этого достаточно.

Фактор соблюдён частично: архитектура не препятствует масштабированию, но автоматическое масштабирование не настроено.

### 9. Disposability

Контейнеры можно быстро остановить и поднять заново через Docker Compose. Данные PostgreSQL вынесены в volume `postgres_data`, поэтому перезапуск контейнеров не уничтожает данные.

API не хранит критическое состояние в памяти процесса. При остановке контейнера состояние приложения сохраняется в базе данных.

Фактор в целом соблюдён.

### 10. Dev/Prod Parity

В development и production используется один и тот же стек:

- ASP.NET Core API;
- Blazor WebAssembly Client;
- PostgreSQL;
- Docker/nginx для production-развёртывания.

Отличия окружений задаются конфигурацией:

- `ASPNETCORE_ENVIRONMENT=Development` или `Production`;
- разные значения `.env`;
- разные frontend appsettings для локального и production-запуска.

Фактор соблюдён частично: локальная разработка может запускаться через `dotnet run`, а production через Docker Compose. Однако основная инфраструктура и база данных совпадают.

### 11. Logs

Приложение пишет логи через стандартный `ILogger`. Логи регистрации, создания тренировок и упражнений пишутся в поток вывода приложения.

В Docker эти логи собираются Docker logging driver и доступны командами:

```bash
docker compose logs api
docker compose logs client
docker compose logs postgres
```

Логи не пишутся вручную в файлы внутри приложения, что соответствует 12-factor подходу.

Фактор соблюдён.

### 12. Admin Processes

Административные задачи выполняются отдельно от основного процесса приложения.

Основной пример — применение миграций базы данных:

```bash
dotnet ef database update
```

На сервере миграции могут запускаться отдельным SDK-контейнером в той же Docker-сети, где работает PostgreSQL.

Фактор соблюдён частично: механизм ручного запуска миграций есть, но отдельный автоматизированный job/service для миграций пока не оформлен.

## Итог

Приложение в основном соответствует принципам 12-factor app:

- конфигурация вынесена в переменные окружения;
- база данных подключается как внешний backing service;
- зависимости объявлены явно;
- приложение контейнеризовано;
- логи пишутся в stdout/stderr и собираются Docker;
- frontend и backend разделены;
- публичный вход идёт через nginx и HTTPS.

Частично требуют развития:

- автоматизация release pipeline;
- отдельный процесс/контейнер для миграций;
- более полное выравнивание dev/prod окружений;
- возможность горизонтального масштабирования API.

Для учебного проекта текущее состояние можно считать хорошей базовой реализацией 12-factor подхода.
